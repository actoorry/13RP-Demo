## 一、P0 定位与核心策略

### 1.1 P0 是什么

**P0 = 一个可运行的功能复现系统 + 一场 15 分钟的国内场景决策演示**。

- **功能复现**：参照 `04_参考资料/功能清单.md`（博宇四方管理端 SaaS 管理系统 V1.0，36 张真实界面截图），全新实现公司架构、商品管理、数据统计、CRM、运营管理五大核心模块，功能逐项对齐，**不是二次开发**（不基于现有系统改造，从零复现功能与数据模型）。
- **决策演示**：在复现的管理端之上，以国内场景（台风"海燕"致宁波舟山港/上海港封港 5 天，某品类供应中断）驱动 13RP 决策闭环：看板报警 → 推演 → 寻优 → 博弈 → 降维输出 5 条指令。

**一句话总结**：博宇自己的管理端（组织/商品/统计/CRM/运营都能点能查），遇到国内台风封港 → 系统 5 分钟推演 342 条路径 → 输出"今天下午 3 点的 5 条可执行指令"。

### 1.2 核心策略：功能复现是真的，决策链路是演的但界面是活的

| 部分 | Demo 中表现 | 实际实现方式 | 观众感知 |
|:----:|-----------|------------|---------|
| **管理端功能**（公司架构/商品/统计/CRM/运营） | ✅ **真**：完整可操作 | Java + Vue3 真实 CRUD + RBAC 权限 | "这就是我们的系统" |
| **4RP 监控看板** | ✅ **真**：实时数据看板 | 模拟数据源 + WebSocket 推送 + ECharts 渲染 | "真正的实时监控" |
| **物流网络图（6RP 孪生简化版）** | ✅ **真**：中国地图节点网络 | ECharts 地图 + 节点/线路动画（港口、仓库、路径） | "全国物流看得见" |
| **7RP 方案推演** | ⚠️ **预计算**：后台跑动画 | 预制的 342 条路径 + 进度条动画 → 回放 | "5 分钟跑了 342 条路径" |
| **8RP 多目标寻优** | ⚠️ **预计算**：预制方案集 | 预制的 3 个帕累托方案 + 雷达图 | "系统自动找到最优解" |
| **9RP 博弈对抗** | ⚠️ **脚本化**：预设结果 | 预设对抗因素 → 胜率变化动画 | "博弈对抗推演完成" |
| **5RP 指令生成** | ⚠️ **模板化**：合同要素模板 | 预制的指令模板（对齐合同要素字段）+ 时间戳自动填充 | "5 条可执行指令" |
| **11-13RP 愿景层** | ❌ **不展示** | P3 才做，Demo 中不出现 | — |

> **关键原则**：管理端功能是**真实可操作的**（增删改查、权限、导出全部可用），观众可以上手点；决策链路是预计算的，但**交互必须是真实的**（点击、勾选、切换都有响应）。一个能点的管理端 + 一条能看的决策链路，胜过一百页 PPT。

### 1.3 为什么是"复现"而不是"二次开发"

| 对比 | 二次开发（在现有系统上改） | 复现（从零实现、功能对齐） |
|------|--------------------------|---------------------------|
| 代码归属 | 依赖既有代码库，历史包袱 | 全新代码，架构可演进 |
| 数据模型 | 受现有表结构约束 | 按功能清单重新建模，对齐 13RP 分层（1RP 资源维等） |
| 演示自由度 | 改动受制于系统 | 完全可控，可嵌入决策演示 |
| 风险 | 现有系统问题难排查 | 从零可控，但工作量更大 |
| P1 演进 | 与 13RP 架构耦合难 | 复现版即为 13RP 管理端基座，直接演进 |

> **决策**：P0 采用复现。复现版同时解决"给客户看什么"和"13RP 自己的底座从哪来"两个问题。

### 2.2 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| **管理端前端** | Vue 3 + Vite + Element Plus + Pinia + TailwindCSS | 与功能清单界面风格对齐（通用后台管理），组件丰富、开发快 |
| **统计图表** | ECharts 5 | 数据总览/用户统计/雷达图/物流网络图统一方案 |
| **物流网络图（6RP 简化）** | ECharts 地图（中国地图 + 节点动画） | 场景 A 是物流网络，2D 地图信息密度更高、加载更快；Three.js 3D 孪生后置 P1（与概念指导书 P0 简化原则一致） |
| **后端** | Java 21 + Spring Boot 3.x + MyBatis-Plus | 与旧方案一致，虚拟线程支持 WebSocket 长连接；MyBatis-Plus 提升 CRUD 开发效率 |
| **数据库** | MySQL 8（业务数据）+ Redis（Token/缓存） | 复现版管理端需要真实数据持久化；Redis 支撑登录态与权限缓存 |
| **认证授权** | JWT + Spring Security + RBAC | 公司架构"角色管理-授权"功能的落地 |
| **模拟数据源** | Java MockDataService（@Scheduled） | 统一技术栈，带高斯噪声的时序数据模拟 |
| **预计算结果** | 手工编排 JSON 方案文件 | 7RP/8RP/9RP 的输出均为预计算 JSON |
| **部署** | Docker Compose 一键启动 | 保证演示环境可复现 |
| **云环境** | 阿里云 ECS（4C/16G）+ 本地备份 | 阿里云主力 + 本地断网备用 |

> **变更说明**：相比旧方案（墨西哥场景版），新增 MySQL/Redis/JWT/RBAC（管理端真实功能需要）；Three.js 孪生降级为 ECharts 2D 物流网络图（国内场景更合适、工作量更省）。

### 2.3 为什么物流网络图用 ECharts 而不是 Three.js

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Three.js 3D 孪生** | 视觉冲击强 | 与"管理端复现"定位不一致（真实管理端是 2D）；开发工作量大（3 周+）；国内场景 3D 建模素材成本高 |
| **方案B（采用）**：ECharts 地图 2D 网络图 | 与统计看板同一技术栈；中国地图 + 港口/仓库节点 + 路径粒子动画足够表达；开发快（1 周）；P1 再上 3D 不冲突 | 视觉冲击不如 3D |

**决策**：P0 采用 ECharts 2D 物流网络图。6RP 数字孪生的概念（事件响应、节点状态、路径高亮）在 2D 上完整保留；P1 升级 Three.js/Unity 时节点数据模型不变。

## 三、15 分钟分镜设计（国内场景）

### 阶段 0：Demo 前准备（观众入场前，-5 分钟）

```
操作人：演示者
动作：
1. 打开浏览器，进入 https://demo.13rp.local（博宇四方管理端）
2. 确认布局正常：
   - 左屏（笔记本）：管理端系统（当前停在"数据统计→数据总览"）

4. 确认鼠标光标、网络、麦克风正常

```

**讲者金句**：

**技术实现**：
- `POST /api/demo/trigger-event` → Orchestrator 将 `eventType=TYPHOON_PORT_CLOSURE` 写入状态机

- ECharts 地图节点颜色切换 `#00D4AA` → `#FF4757` + 波纹特效（effectScatter）

### 阶段 2：系统自动推演（3 分钟）

**操作序列**：

| 时间 | 操作 | 系统反应 |
|:---:|------|---------|
| 2:00 | （无需操作，自动运行） | 物流网络图：各港口/仓库之间物流链路动态闪烁（宁波→青岛、宁波→天津、上海→苏州仓库等） |
| 2:30 | — | 屏幕中央进度条 0% → 100%（约 2 分钟动画），文本显示"推演中…已跑完 127/342 条路径""正在进行第 487 次蒙特卡洛扰动…" |
| 3:30 | — | 进度条右侧缩略显示正在跑的路径：①改港青岛+铁路转运 ②空运关键物料 ③启用备选供应商 |
| 4:00 | — | 路径跑完，弹窗："方案推演完成。共评估 342 条路径，筛选出 3 条可行路径。是否启动 8RP 多目标寻优？" |
| 4:30 | 演示者讲解推演概念，引导观众注意雷达图 | — |
| 4:45 | 点击"启动寻优" | 进入阶段 3 |

**讲者金句**：

> "传统做法：打电话、开会、拍脑袋，至少半天。13RP：5 分钟内在平行宇宙里把能走的路全部走一遍。342 条路径、1000 次随机扰动——'不确定性'被量化成了'概率'。"

**技术实现**：
- 推演进度条是**预编排动画**（不是真实计算），时长约 120 秒
- Java `ScheduledExecutorService` 每 0.5 秒更新进度值并通过 WebSocket 推送
- 路径文本在 6 个预制路径池中随机轮换显示（模拟真实计算感）
- 预制 JSON 结构：
```json
{
  "total_paths": 342,
  "simulated": 342,
  "perturbations": 1000,
  "top_paths": [
    {"id": "P1", "name": "改港青岛+铁路转运", "cost": 120, "carbon": 45, "delivery": 7, "risk_score": 0.22},
    {"id": "P2", "name": "空运关键物料", "cost": 340, "carbon": 210, "delivery": 2, "risk_score": 0.15},
    {"id": "P3", "name": "启用备选供应商", "cost": 80, "carbon": 12, "delivery": 10, "risk_score": 0.38}
  ]
}
```

### 阶段 4：博弈对抗（3 分钟）

**操作序列**：

| 时间 | 操作 | 系统反应 |
|:---:|------|---------|
| 8:00 | 博弈面板展开，显示 4 个对抗因素（el-checkbox 列表） | 默认已勾选前 2 个 |
| 8:15 | 演示者点击"运行博弈对抗" | 博弈动画：方案卡片左右震荡 + 胜率数字滚动变化 |
| 8:45 | — | 结果显示：P2 空运胜率 78%→61%，P1 改港胜率 65%→69%（反超） |
| 9:15 | 演示者分别切换勾选/取消对抗因素 | 胜率实时重算（预计算），观众看到不同变量组合下结论的剧烈变化 |
| 9:45 | 演示者讲解博弈的价值 | 改港路线在物流网络图中高亮闪烁 |
| 10:30 | 点击"确认方案：改港青岛 P1" | 进入阶段 5 |

**对抗因素池**（国内场景版）：

| 对抗因素 | 效果 |
|---------|------|
| ☑ 港口拥堵加剧（青岛/天津也受影响） | 改港方案时效优势被削弱 |
| ☑ 竞争对手抢订舱位 | 空运/海运成本上升 |
| ☐ 台风路径延长（封港 7 天） | 所有海运方案风险上升 |
| ☐ 客户接受延期（同意 10 天） | 备选供应商方案胜率上升 |

**讲者金句**：

> "刚才空运方案胜率 78%。现在加入两个新变量：港口拥堵加剧、竞争对手抢订舱位——空运的胜率掉到了 61%，而改港补货反超到 69%。13RP 把看不见的变量也拉进来一起算。"

> "别人家的系统告诉您'发生了什么'——库存不足、物流中断。13RP 告诉您'现在该做什么'——5 条指令，精确到负责人、截止时间、关联单据号。每条指令下面都有一行小字——'什么条件下会失效'。这是 13RP 最重要的设计原则：可证伪性。"
